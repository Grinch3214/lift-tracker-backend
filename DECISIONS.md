## Technical

- **ORM — решено: TypeORM.** Изначально (`ARCHITECTURE.md` v1) сознательно стартовали без ORM — сырой `pg`, чтобы сначала понять SQL/JOIN/constraints/транзакции руками, ORM подключить отдельным этапом позже (см. историю коммитов). План изменился: SQL продолжаю разбирать отдельно (задачки/практика вне проекта), а сам проект пишем сразу максимально правильно с точки зрения продакшена — ORM с самого начала, а не как надстройка поверх ручного `pg`-слоя.
  - TypeORM выбран за официальную интеграцию с NestJS (`@nestjs/typeorm`) и максимум документации именно под связку Nest+TypeORM+Postgres. Известный минус — менее надёжная автогенерация миграций, чем у Prisma; компенсируется тем, что миграции всё равно нужно перечитывать перед применением.
  - Ручные SQL-миграции (`migrations/0001-0004`) и `src/database/database.module.ts` (голый `pg.Pool`) были первым проходом до этого решения. 2026-09-02: базу пересобрали с нуля через 5 отдельных TypeORM-миграций (`src/migrations/CreateUsers`/`CreateRefreshTokens`/`CreateWorkouts`/`CreateWorkoutExercises`/`CreateSetEntries`, по одной таблице за шаг — сгенерированы через временное сужение `entities` в `data-source.ts` до нужного подмножества на каждом шаге) — старую папку `migrations/` удалили полностью, `src/migrations/` теперь единственный источник правды по схеме. Причина: до этого TypeORM ничего не знал о существовании `users`/`workouts`/`workout_exercises`/`set_entries` (их создавали руками до перехода на ORM) — его собственная таблица `migrations` содержала только `refresh_tokens`, то есть `npm run migration:run` на чистой БД с нуля не собрал бы схему целиком.
